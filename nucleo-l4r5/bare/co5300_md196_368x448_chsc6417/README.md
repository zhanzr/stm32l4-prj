# co5300_md196_368x448_chsc6417 - CO5300 1.96" 368x448 LCM over single-lane SPI + CHSC6417 touch

Drives the **TK0196M106** 1.96" **368x448** module - **CO5300** LCD
controller plus **CHSC6417** capacitive touch - on the **nucleo-l4r5**
board (STM32L4R5ZIT6 @ 120 MHz), over **plain single-lane SPI**.
Ported from the nucleo-u575 project of the same name (**identical module
wiring**); that port copied `nv3030b_md183_240x284_cst816d` (same bus,
same three wires, same demo loop, SOFT/HW bus ladder). Vendor references:
the **TK499 TK0196M106** single-lane example (display init, vendor
verbatim) and the vendor **ESP32 QSPI** example's
`esp_lcd_touch_chsc6417` component (touch protocol).

## Protocol (wrapped command)

Every transaction is ONE chip-select frame:

```
CS low
02 00 <cmd> 00          <- 4-byte header (opcode, 0, command, 0)
... parameter / pixel bytes ...
CS high
```

- The `02` prefix is the **1-data-line transfer opcode** (the vendor
  TK499 `WriteComm` sends exactly this; the vendor QSPI example's pixel
  burst uses the 4-line opcode `32h` - with only IO0 wired, `02h` is
  the single-line form of the same transfer).
- Pixel bursts are row-chunked transactions: window set once (2Ah/2Bh),
  first row as 2Ch, further rows as 3Ch (write memory continue).
- SPI mode 3, MSB first. Write-only: no readback anywhere in the
  driver; MISO is not wired.

## Vendor init sequence (CO5300, verbatim from the TK499 example)

```
FE 00            command access unlock
11  (sleep out)  + 100 ms
FE 00
C4 80
3A 55            16bpp RGB565
53 20            display control (BCTRL=1: enables the 51h brightness)
63 FF            HBM brightness (inert - HBM_EN (66h) defaults to 0)
51 60            display brightness (see the brightness section below)
58 07
29  (display on) + 80 ms
```

The sleep-out step is `11h` + **120 ms**: the datasheet says *"It takes
120msec to become Sleep Out mode (booster on mode) after SLPOUT command
issued"*. The vendor sequence uses 100 ms; this driver waits the full
120 ms so the panel is certainly in booster-on mode before the pixels.

The vendor example hardware-resets the panel first; this wiring has no
reset pin, so the POR settle rides on `LCD_POWER_SETTLE_MS` (500 ms)
before the first clock.

**Do not "fix" this by sending the CO5300 software reset (01h).** The
datasheet forbids the sequence that would need:

> *It will be necessary to wait 5msec before sending new command
> following software reset. […] If Software Reset is applied during Sleep
> Out mode, it will be necessary to wait 120msec before sending Sleep Out
> command. Software Reset command cannot be sent during Sleep Out
> sequence.*

`LCD_Reinit()` does reset -> sleep out -> init, so a `01h` there needs a
120 ms hold and a fresh sleep-out. Sending `01h` and carrying straight on
(an earlier revision did) leaves the panel behind that rule and it stops
accepting pixels: at 1.8 MHz the bit-bang tolerates it, at the HW SPI1
rates the pass goes black. See the `LCD_RESET()` note in `src/lcd.c`.

## The SOFT/HW bus ladder

Same as the nv3030b project: the demo alternates **SOFT (bit-banged)**
and **HW (SPI1)** passes on the same three wires, each from a full
re-init, so a difference between the passes isolates the SPI engine
itself. Cold-boot bring-up tiles the 64x64 RGB565 asset (see
`tools/`, regenerated by `png_to_rgb565.py`) interleaved with
`LCD_Reinit()` cycles. Per pass: checkerboard stress, TEST_STAND vendor
screens (timed solid fills), info pages, HSV gradient, LED test, live
FPS, touch printout.

## Wiring

| Module pin | MCU pin | Feature |
| ---------- | ------- | ------- |
| QSPI_CS   | **PA4** | chip select (software GPIO, both transports) |
| QSPI_CLK  | **PA5** | SCK (GPIO on SOFT; SPI1_SCK AF5 on HW) |
| QSPI_IO0  | **PA7** | single data line (GPIO on SOFT; SPI1_MOSI AF5 on HW) |
| RST / BL / DC | - | not wired (POR settle in software; brightness = command 51h; wrapped protocol) |
| TOUCH_SCL | **PB8** | I2C1_SCL (AF4, hardware) |
| TOUCH_SDA | **PB9** | I2C1_SDA (AF4, hardware) |

Common GND between the module and the board is required.

## Brightness

There is no backlight pin - the panel is an OLED, so brightness is a DCS
register (**51h**, WRDISBV). The datasheet defines it as a plain linear
ratio, `DBV/256`:

| value | 0xFF | 0xC0 | 0xA0 | 0x80 | 0x60 | 0x40 | 0x20 | **0x01** |
| ----- | ---- | ---- | ---- | ---- | ---- | ---- | ---- | -------- |
| %     | 100  | 75   | 62.5 | 50   | 37.5 | 25   | 12.5 | **0.78** |

The vendor sequence - and the vendor ESP32 example - write `0xA0` (62.5
%), which on this board reads far brighter than the other LCD modules, so
the default here is **`0x01` = 0.78 %, the lowest value that still shows
an image**. (`0x00` is the true floor but it is 0 % - the panel renders
nothing at all.) Tune at build time:

```bash
bash build.sh -DLCD_BRIGHTNESS=0x40      # 25 %, if 0x01 is too dim
```

### Why there is no room below 51h

`51h` is the **only** brightness control the datasheet offers:

- `7.4 Command List` enumerates **CMD1 only**. The CMD2 pages that would
  hold panel-current controls (Gamma, OLED IP, PWR Control, reachable via
  `FEh`) are **not documented**, so there is no spec'd deeper lever to
  lower. Driving undocumented registers blind on an OLED is not done.
- `63h` (WRHBMDISBV, HBM brightness) is written `0xFF`, but `HBM_EN`
  (`66h`) defaults to **0 = disabled**, so that register is inert.
  Enabling it would be a *boost* and would leave normal mode.
- `53h` (WRCTRLD) is written `0x20`: its `BC_EN` bit (D5) must be 1 for
  `51h` to take effect at all, and `DIM_EN` (D3) is left 0. Note the
  datasheet power-on default is `0x28` (both bits set); `0x20` is what the
  vendor sequence uses, kept verbatim.
- `CABC`/`ACL` analyse content and would distort colours rather than act
  as a level control.

So if `0x01` is still perceived as bright, that is the panel's own
emission at minimum drive - the remaining control is analog (panel/OLED
supply), not a register.

## Touch: CHSC6417 over hardware I2C1

PB8/PB9 are the I2C1 AF4 pins: 100 kHz standard mode (vendor runs
400 kHz - raise `CTP_TIMINGR` once the wiring is proven). 7-bit slave
address **0x2E**. The touch data block is read from register **0x00**
(three vendor sources agree on that - the TK013F1327 example, the
espressif `esp_lcd_touch_chsc6417` header, and the f4-demo
`jd9858_md130_360x360_chsc6417` port; the register byte in that
espressif component's own read call, 0xE0, contradicts its header and
reads back a constant): byte 0 = {[1:0] point count, bit 6 = X bit 9,
bit 7 = Y bit 9}, byte 1 = X[7:0], byte 2 = Y[7:0]. Chip ID at register
0xA7 (printed at boot). The console prints
`[TOUCH] down X=.. Y=.. (448-Y=..)` / `[TOUCH] release`.

## Geometry / knobs

- 368x448, 16bpp. The vendor demo drives columns 0..367 directly, so
  `LCD_X_OFFSET` defaults to 0. The same vendor file's commented-out
  full window is `2Ah = 0010h..017Fh` - if the image comes out shifted,
  build with `-DLCD_X_OFFSET=16`.
- `LCD_SPI_PRESC`: SPI1 prescaler, the build-time default rate. Set to
  **/4 = 30 MHz**, the highest rung at or below the panel's ~47 MHz write
  limit (the L4 prescaler is powers of two, so there is no 40/45 MHz
  step; the U5 ran 40 MHz from its 160 MHz APB2). `/2 = 60 MHz` was tried
  and is **too fast** - it corrupts the checkerboard on this module.
  Step down if a build needs it:
  ```bash
  bash build.sh -DLCD_SPI_PRESC=SPI_BAUDRATEPRESCALER_8    # 15 MHz
  bash build.sh -DLCD_SPI_PRESC=SPI_BAUDRATEPRESCALER_16   # 7.5 MHz
  ```
  Ladder: /2 = 60, /4 = 30, /8 = 15, /16 = 7.5 MHz, /32 = 3.75 MHz,
  /64 = 1.875 MHz, /128 = 937 kHz, /256 = 468 kHz.
- `LCD_SPEED_SWEEP`: default on. Every third demo round the HW prescaler
  is climbed (**1.875 -> 30 MHz**; 60 MHz is excluded, see above) and the
  timed checkerboard is run at each rung, so the usable ceiling is found
  from the console log in one flash rather than one rebuild per rung. Set
  `-DLCD_SPEED_SWEEP=0` to remove the detour (it also leaves the last
  rung's checkerboard on screen). The sweep is a runtime form of
  `LCD_SPI_PRESC`; both go through `QSPI_SetPrescaler()` in
  `interface.c`.
- `LCD_HW_CS_SETUP` / `LCD_HW_CS_HOLD` / `LCD_HW_CS_IDLE`: busy-loop
  counts (~40 ns each) giving the HW path the CS margins the bit-bang
  gets for free (the settle loop plus the first byte's delay). Each byte
  of CS-to-first-edge time is one the SPI peripheral would otherwise
  spend clocking - at 15 MHz that is only ~66 ns without them.
- `LCD_BRIGHTNESS` (51h): default `0x01` = 0.78 %, the lowest value that
  still shows an image. See the Brightness section.
- `LCD_BRINGUP_PASSES`: default `2` fill+reinit cycles at cold boot.
  This is the main bring-up **time** knob - each cycle costs one fill
  (a few hundred ms on HW SPI1: the L4 SPI HAL paces one byte per flag
  poll, so the 368x448 fill is CPU-bound, not wire-bound - the measured
  value is printed by the info page) plus an `LCD_Reinit()` (~250 ms of
  datasheet delays). Drop to `1` for the fastest boot, raise to `3` if a
  cold power-on ever shows a blank panel:
  ```bash
  bash build.sh -DLCD_BRINGUP_PASSES=1
  ```
  The panel on this board comes up on the first init, so 1 is normally
  enough - the second pass is insurance for a slow-starting panel.
- No reset pin: **power-cycle the MODULE** before judging a fix. Note the
  CO5300 software reset (01h) is deliberately **not** used - see the
  warning in the vendor-init section above.

## Port notes (L4 vs. U5)

The module, its wiring and the CO5300/CHSC6417 protocols are identical to
the nucleo-u575 project; only the SPI engine and clock tree differ:

- **The HW path does not use `HAL_SPI_Transmit`.** On the L4 that
  function opens every `SPI_DIRECTION_1LINE` transfer with
  `__HAL_SPI_DISABLE()` + `SPI_1LINE_TX()` (to set `BIDIOE`) and
  re-enables `SPE` afterwards. `SPE` falling releases SCK/MOSI from the
  peripheral **mid-frame**, so with CS already low the panel latches that
  edge as an extra bit and the wrapped stream shifts - the hardware pass
  comes out malformed while the bit-bang (which never touches `SPE`) is
  fine. The U5 port dodged this with `MasterKeepIOState`, which the L4 IP
  does not have. This port instead configures SPI1 as
  **`SPI_DIRECTION_2LINES`** (MISO is not wired, so the RX side is
  ignored) and drives the data register directly in `hw_tx()`, leaving
  `SPE` set for the whole frame. That is also faster: no per-byte HAL
  flag polling and no RX-FIFO drain per call.
- **SPI prescaler field.** The U5 IP keeps it in `SPI_CFG1`'s `MBR` bits,
  the L4 IP in `CR1`'s `BR` bits - `QSPI_KHz()` decodes the latter here.
- **Console** is LPUART1 PG7/PG8, not USART1 PA9/PA10.

### Rate: 30 MHz, and why not 60

The U5 project ran this panel at 40 MHz. On the L4 the prescaler is powers
of two, so the rungs around that are **30 MHz (/4)** and **60 MHz (/2)**.
60 MHz was tried and **corrupts the checkerboard**; 30 MHz is clean, so
that is the default - the highest rung at or below the panel's ~47 MHz
write limit.

The initial bring-up deliberately started at **/64 = 1.875 MHz**, the same
order as the bit-bang, so HW and SOFT could be A/B'd at equal wire speed.
That isolated the failure: SOFT clean + HW malformed at equal rate proved
the problem was in the SPI engine (framing/CS timing), not clock speed.
The missing piece was **CS setup/hold time** - the bit-bang leaves
microseconds between CS and the first clock edge for free, while the SPI
peripheral starts clocking within one SCK period. `LCD_HW_CS_SETUP` /
`_HOLD` / `_IDLE` (each ~1 us) supply that; with them, HW is stable at
every rate up to 30 MHz.

The L4 SPI HAL also paces transfers per byte (`TXE`, no FIFO like the U5),
so the fill time was dominated by firmware overhead rather than SCK - the
same effect the `st7789s_md120_240x240_ft6336` port documents (105 ms at
60 MHz vs 122 ms at 30 MHz). `hw_tx()` writes `DR` directly and drops that
overhead, and the bus is now armed once per mode switch instead of
re-muxing the pins on every transaction.
